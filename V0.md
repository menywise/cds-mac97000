# CDS — Référentiel V0

**Validé le 28 septembre 2026.** Ce fichier fixe le périmètre de la V0 : ce qui doit exister, fonctionner à 100 % et être désactivable avant toute duplication.

Règle d'or : **l'existant d'abord, 100 % fiable. On ajoute ensuite, un module à la fois, par itération propre.**

Contraintes :

- Le dépôt reste 100 % compatible Lovable (aucune réécriture d'historique, branche toujours fonctionnelle).
- Pas de crédits Lovable : chaque changement de base est livré en migration dans `supabase/migrations/` **et** exécuté à la main dans l'éditeur SQL. Les migrations sont écrites pour pouvoir être rejouées sans danger.
- Chaque migration est testée en local avant livraison : `tests/db/run.sh` (voir en bas).

## 0. Décisions de cadrage (28 septembre 2026)

- **Destination** : ce dépôt sert à lancer les **projets propres du studio** de création d'entreprise (pas de clients tiers). « Vendable » = chaque projet doit pouvoir être monétisé ou revendu.
- **Règle d'adoption** : on adopte une brique externe (hébergée sur Coolify) seulement si sa valeur dépasse le coût d'un second système (autre compte, autre admin, autre serveur). Sinon, on garde le module dans ce dépôt.
- **Briques externes retenues** (source : `BLUEPRINT_CONSTELLATION_HOLOKAI.md`, 21/08/2026) : Ghost (magazine, newsletter, abonnements payants), Revive Adserver (régie), Umami (audience), Shlink (liens courts), Meilisearch (recherche, quand le volume l'exige). Avant adoption, chaque brique repasse la grille : licence MIT/Apache, Docker, API, dernier commit < 6 mois.
- **Gardés dans ce dépôt** : socle (comptes Supabase partagés, admin, légal, SEO), **forum** (simple, déjà intégré aux membres et à la messagerie ; aucun forum MIT ne partage nos comptes), **annuaire + géographie** et **petites annonces** (aucun équivalent libre mûr).
- **Conséquences** : le module Blog reste minimal (Ghost prend le magazine), la Régie (17) devient un simple emplacement qui affiche une zone Revive, la Mesure d'audience (J) = intégration Umami, pas de code.

## 4. Définition de « fini » pour un module

1. Interrupteur en base, dépendances respectées.
2. Éteint : aucune trace (pages → accueil, menus, pied de page, sitemap, admin).
3. Règles d'accès testées pour visiteur, membre, admin (`tests/db/`).
4. Admin complet : créer, lire, modifier, supprimer, modérer.
5. Chaque page gère chargement, vide, erreur, introuvable.
6. SEO sur chaque page publique.
7. Au moins un test automatique.
8. Ligne cochée dans la grille de conformité.

- **Recette automatisée** (inspirée de Goldwing `admin.recettage.tsx` + `qa-checklist.ts`) : plan unique `src/lib/qa-plan.ts` (81 pages + 18 contrôles manuels). Le robot Playwright ouvre chaque page en visiteur, membre et admin, sur ordinateur (1366 px) et mobile (360 px). Échec si : page blanche, erreur console ou JavaScript, réponse 5xx, débordement horizontal, pas de h1, page d'un module éteint accessible, page protégée ouverte à un visiteur. Lecture seule : il bloque toute écriture en base. Sans contenu publié, il vérifie la page « introuvable » de l'adresse. Membre et admin : vrais comptes par variables d'environnement, sinon session et base **simulées** (vérifie que chaque écran tient debout avec des données vides). Écran `/admin/recettage` : import du rapport `recette.json`, contrôles manuels à cocher.
- **Défauts trouvés par le robot et corrigés** : (1) toute page de l'espace connecté ouverte sans session provoquait une erreur React d'hydratation (redirection vers la connexion pendant l'hydratation) → contrôle de session déplacé dans le composant ; (2) même erreur pour une page admin d'un module éteint → la route racine renvoie à l'accueil **dès le serveur** (`PROTECTED_PATH_MODULES` dans `src/config/modules.ts`, à tenir à jour pour chaque nouvel écran) ; (3) le bouton « Signaler » lisait l'adresse dans `window` → écart serveur/navigateur, corrigé.
- **Module D « Paiement »** (`payments`, éteint, exige `lms`), repris de Goldwing sans SDK : `startCourseCheckout` (serveur) crée une ligne `payments` puis une session Stripe Checkout ; le **montant vient de la base**, jamais du navigateur. Webhook `/api/stripe-webhook` : signature vérifiée avant tout (HMAC, 5 min de tolérance), traitements idempotents en base (`payment_mark_paid` vérifie montant et devise et ouvre l'inscription, `payment_mark_status` pour expiration/échec, `payment_mark_refunded` referme l'accès). Fonctions réservées à la clé de service. **Clés Stripe en secrets d'environnement uniquement.** Case de renonciation au droit de rétractation (L221-28 13°, reprise de Goldwing) obligatoire, datée avec le paiement. Écran `/admin/paiements` : état de la configuration (jamais la clé), liste, total encaissé, export CSV. Paiement conservé 10 ans, anonymisé à la suppression du compte. CGV et confidentialité complétées (visibles module allumé).
- **Page formation** : payante non réglée = bouton « Payer » (module allumé) ou « place réservée » (module éteint, règlement saisi par l'admin comme au lot 4). Corrige au passage un défaut : un inscrit non réglé voyait « Reprendre la formation » et des leçons cliquables.
- **Signalements** (`reports`, allumé), repris de Goldwing : bouton « Signaler » sur articles, commentaires, discussions et réponses du forum, avis, témoignages, fiches et avis de l'annuaire, annonces, profils. Membres seulement (le visiteur est envoyé vers la connexion), jamais sur son propre contenu. En base : 10 signalements par 24 h, pas de doublon en attente, adresse interne seulement, signaleur invisible des autres membres, traitement daté et signé par la base. Écran `/admin/signalements` : à examiner, action prise, écarté, rouvrir, note interne.
- **Purge des messages de contact** : `purge_contact_messages()` efface ce dont le dernier échange a plus de 3 ans ; planifiée chaque nuit à 03:17 par `pg_cron` (activé par la migration si disponible), bouton « Purger maintenant » dans la boîte de réception.
- **Grille de conformité** : 4 lignes ajoutées (paiement « à vérifier » tant que le parcours de test Stripe n'est pas fait).

**Lancer la recette** : `npm i --no-save playwright` puis `npx vite dev --port 8080` et `node tests/e2e/recette.ts`. Comptes réels facultatifs : `CDS_RECETTE_MEMBRE_EMAIL`/`_MDP`, `CDS_RECETTE_ADMIN_EMAIL`/`_MDP`. Derrière un proxy qui réécrit TLS : `CDS_RECETTE_CHROMIUM_ARGS="--ignore-certificate-errors-spki-list=<empreinte>"`.

Limites connues : paiement unique seulement (pas d'abonnement aux offres de la page Tarifs) ; pas de facture générée par le site (Stripe envoie le reçu) ; la recette en rôle simulé ne voit pas les vraies données (fournir des comptes de test pour la recette réelle) ; le robot n'est pas branché sur une intégration continue (aucune en place).
